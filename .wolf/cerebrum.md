## Do-Not-Repeat

<!-- Mistakes made and corrected. Each entry prevents the same mistake recurring. -->
<!-- Format: [YYYY-MM-DD] Description of what went wrong and what to do instead. -->
- [2026-07-21] Don't reveal a container with gsap `autoAlpha` (or otherwise toggle visibility:hidden) if you need to `focus()` a control inside it in the same tick — a visibility:hidden ancestor makes the element unfocusable, so focus silently no-ops. Use `opacity` for the reveal, or move focus in the tween's onComplete.
- [2026-07-21] A keydown-based focus trap (intercept Tab on the container) CANNOT contain focus across a cross-origin iframe (e.g. a reCAPTCHA checkbox) — keydown/Tab events inside the frame don't bubble to the parent, so focus leaks out. Use focus SENTINELS instead: an empty `tabIndex={0}` guard element as the first and last child of the dialog whose `onFocus` bounces focus to the opposite end. Same reason, Esc-to-close won't fire while focus is inside the cross-origin frame (acceptable; Close button + backdrop still work).
- [2026-07-21] When computing a focus trap's first/last focusable, filter out elements that are hidden (`el.offsetParent === null`) or `tabIndex === -1`. Third-party widgets (reCAPTCHA injects a hidden `textarea[name=g-recaptcha-response]`) and honeypots (`display:none`, tabindex -1) otherwise get picked as the "last" focusable, and `.focus()` on a hidden element no-ops — so the wrap silently fails.
- [2026-07-21] `grecaptcha.render()` throws "reCAPTCHA has already been rendered in this element" under React StrictMode (dev double-invokes effects on the same DOM node). Guard the render with a `renderedRef` (render once) — do NOT let the render promise's `.catch` blindly set an error state, or the benign dev double-render trips it (prod has no StrictMode so it only breaks dev/verify). Also: a captcha solve fires inside a cross-origin iframe and causes NO React re-render — always drive the submit gate from a state value set by the widget's `callback`, never by polling `grecaptcha.getResponse()` at render time.
- [2026-07-21] Two overlapping `backdrop-filter` layers + unmounting the top one = Chromium drops the lower layer's blur until a repaint (seen: closing the hello drawer killed the nav's blur until next scroll). Don't stack backdrop-filters; the drawer backdrop uses a plain translucent `bg-navy/75` instead of `backdrop-blur-sm`. Separately, ST+Lenis desync after `scrollIntoView`+programmatic scroll is a harness artifact (reproduces with no drawer) — don't chase it as a product bug.
- [2026-07-21] Two sibling elements at the same position in a `{cond ? <div> : <div>}` swap are RE-USED by React (same tag → same DOM node). If you animate one with gsap (leaving inline `opacity`/`visibility`/`transform`), those styles carry over to the other branch. Symptom seen: the brief opened invisible/unclickable because the CTA's fade-out `autoAlpha:0` stuck to the reused node. Fix: give the branches distinct `key`s so each mounts fresh. Diagnostic tell: `getBoundingClientRect` reports a box but `document.elementFromPoint` at that box returns an ancestor, and synthetic `el.click()` works while real `page.click`/`page.type` don't (hidden elements reject real events but accept synthetic ones).
- [2026-07-21] CORRECTION to the note above: that "scroll past position → class dropped" was NOT just a harness artifact — it was a real bug. Never give an always-on scroll-STATE trigger an upper bound. A `ScrollTrigger.create({ start, end, toggleClass })` DEACTIVATES past `end:"max"` and toggleClass strips the class at the bottom (worse when the cached max is stale after page-height changes). For "scrolled past N" styling use an unbounded `start:0 end:"max"` with a manual `onUpdate/onRefresh` toggle on `self.scroll() > N`, set the initial state on mount, and DON'T gate it behind prefers-reduced-motion (scroll-state styling ≠ motion). See Nav.tsx / bug-016.
